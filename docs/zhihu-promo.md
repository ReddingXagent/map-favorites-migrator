这个问题我研究了两天，最后把自己写的工具跑通了，318 个收藏导进高德 307 个。把踩的坑和工具都放这儿。

## 先说结论

**高德没有官方导入功能，百度也没有。两家的开放平台 Key 都不管用。**

我试过的死路：

- 高德开放平台 Web 服务 Key → `/v3/favorite/add` 直接返回 `SERVICE_NOT_AVAILABLE`。查了一圈文档才明白：**Key 只能查，不能写**。收藏属于账号数据，得用用户登录态。
- 网上流传的「百度地图收藏夹 SDK」→ 那是**安卓 SDK 的本地收藏夹**，只存在手机 App 自己的 data 目录里，跟账号云端收藏完全不互通。
- 各种所谓「一键迁移」网站 → 要么收费，要么要你账号密码。

## 可行方案

直接用两个网页端自己的收藏接口，走你浏览器的登录态。

**① 抓百度收藏**

打开 `map.baidu.com` 登录，F12 控制台执行一段脚本，走 `qt=fav&mode=get&type=favdata` 接口。

这里有个**大坑**：这个接口返回的是**增量变更流**，不是收藏列表。同一条收藏会出现 `add` / `modify` / `del` 多条记录。

我第一版代码写的是 `filter(x => x.action === 'add')`，结果只拿到 **102 条**，而手机 App 显示 **319 条**。

正确做法：按 `sid` 分组，取 `ver` 最大的那条，再剔除 `action === 'del'`。这样才拿到真实的 318 条。

判断拉完的依据也不是「页码不变」，而是响应里的 `sync.newnum`（服务端剩余条数）归零。

**② 坐标转换**

百度用的 `geoptx/geopty` 是 **BD09 墨卡托坐标**。网上流传最广的那份「百度官方 MC2LL 系数表」（`LLBAND` + `LL2MC` 六档），我实测下来偏了 **700 米**。

自己反推校准出来的公式：

```
经度：lng = degrees(x / 6378551.0)
纬度：迭代解 y = (171.233889·lat + 6335150.13)·ln(tan(π/4 + lat/2))
```

对比 6 个已知 POI，误差压到 **25 米以内**。

还有个容易多此一举的地方：反解出来**已经是 GCJ-02 量级**了，不要再叠加一次 BD09→GCJ-02 的偏移，否则又偏 700 米。

**③ 写入高德**

高德 2026 版把 `addFav` 和 `syncFaves` 都下线了，新接口是 `/api/favorite/add`，一条一条加。但老页面 `ditu.amap.com/faves?innersrc=uriapi` 上 `syncFaves` 还能用，走的是「读全量 → 合并 → 一次性同步」，比逐条加稳得多。

这里也有两个坑：

- **一次性提交几百条会被静默丢弃**。接口返回 `status: 1`，看起来成功，但服务端不落盘。必须分批，50 条一批，每批提交前重读版本号。
- **单账号收藏上限约 300 条**。我到 307 条以后，剩下 32 条怎么提交都进不去。重试 3 轮无果，确认是硬上限。

所以最终是 **318 → 307**，差的 32 条导成了 CSV 留底。

**④ 页面渲染**

顺便说个玄学问题：高德页面在部分 Chrome profile 下渲染失败，`window.amap` 根本挂不上，页面一片空白。

解决办法：**换一个全新的 user-data-dir 起 Chrome**，加上 `--disable-extensions`，立刻正常。日常 profile 里的扩展或缓存会污染页面。

## 工具

我把整套流程整理成开源命令行了，MIT 协议：

**https://github.com/ReddingXagent/map-favorites-migrator**

```bash
pip install -e .

mfm fetch baidu --out fetch.js      # 生成抓取脚本
mfm parse baidu --input raw.json --out baidu.json
mfm convert --from baidu --to amap --input baidu.json --out import.js
mfm redact --input baidu.json --out clean.json    # 脱敏
mfm export --format csv
```

支持**双向**：百度↔高德都能转。坐标往返误差 <1 米。

内置脱敏（手机号、身份证、门牌号打码，坐标降精度），分享数据前跑一下。

全程本地运行，不经过任何第三方服务器，代码全部开源可审。

## 最后

建议先拿小样本试，比如先导 10 条看位置对不对。高德那边满了 300 条就得先删旧收藏腾位。

有更好的方案欢迎讨论，尤其是高德那条 300 上限，我在想有没有办法绕过。

### 预设 Q&A

**Q：用这个会不会封号？**
A：走的是网页端正常接口，频率控制得比手动点击还低（50 条一批，间隔 3 秒）。但不保证，高德改接口就失效，所以工具开源，坏了能自己修。

**Q：为什么不直接用官方 API？**
A：官方 Web 服务 API 没有收藏写入能力，只有查询。收藏是账号数据，必须用户态。

**Q：300 条上限有办法绕过吗？**
A：目前没找到。试过分批、换时间、换 IP，都无效。猜测是账号维度硬限制。

**Q：数据安全吗？**
A：全程本地，只跟你浏览器登录的官网通信。脱敏功能会自检残留。
